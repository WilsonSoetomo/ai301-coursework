# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (its Diagnosis section), read against the repro-evidence block's steps, artifacts, and control runs. | Passes if the stated cause is consistent with every control run and artifact in the repro evidence and the plan cites at least one of them by name — this includes an inferred mechanism (no single artifact shows the cause directly, e.g. no debug trace of it) as long as it explains every control's result and none contradicts it. Fails if any control run or artifact contradicts the stated cause (e.g. a control that isolates a different site, or a step showing the "culprit" behaves fine outside the failing path). `unclear` is reserved for a diagnosis that cites no repro evidence at all, or evidence that has nothing to do with the claimed cause either way — not for a cause that is inferred rather than directly witnessed. |  required |
| scope-bounded | The plan's Scope and Files/Approach, read against the diagnosis: is the touched surface the one the diagnosis implicates, or wider? | Passes if every in-scope item is a change at the site(s) the diagnosis names, and anything beyond that site is explicitly named as deferred (not built now) with a reason, rather than folded into the approach as work to do. Fails if the approach includes a rewrite, migration, abstraction, new option, or "while I'm in there" change the diagnosis does not require, even when the core fix inside it is correct. |  required |
| executable | The plan's Files and Approach, read as a stranger with no access to the author would read them. | Passes if specific files or code sites are named, a single chosen approach is stated (not a menu of options left open), and the steps are ordered enough that a stranger could start work without first asking the author a clarifying question. Fails on undecided branches left to build time ("gocui or tcell, not sure", "upstream or vendored, whichever is easier"), on "investigate X" with no named site, or on a plan naming no files at all. |  required |
| test-plan-decisive | The plan's Test plan, read against the repro evidence's steps and artifacts. | Passes if the test plan names a specific, observable check tied to the diagnosed fix: re-running the repro's exact steps and stating the expected before/after (an error becomes success, an exit code changes, a value matches), a named fixture, or an equivalent concrete assertion. Fails on a subjective outcome ("should feel fast", "nothing else should feel broken") or a plan that only says to run the existing suite with no assertion about the fix's own observable behavior. |  required |
| thread-aware | The Thread highlights, read against the plan's Approach and the plan comment. | When a thread highlight states an explicit maintainer diagnosis, requested test, or a rejected approach, the plan's approach and comment engage it: adopt it, act on the requested test, or state a reasoned divergence. Fails when the plan silently pursues a different path (e.g. a workaround) while a maintainer already named the actual culprit and asked for something in-thread. Passes automatically when no thread highlight states a direction to engage. |  required |
| ai-disclosure | The repo-facts block's contribution policy AI-use line, read against the candidate plan comment. Every package here is AI-assisted work by default; a comment saying nothing about AI is not evidence none was used. | If the stated policy requires disclosing AI assistance in comments, the plan comment must contain an explicit disclosure sentence naming the tool and the extent of help; its absence fails this check even if the plan itself is otherwise ready. If the policy instead asks for the comment to be in the human's own words, judge the comment's voice against that. If the policy is silent on comments or reaches only PR code, this check passes automatically. |  required |
| unknowns-labeled | The plan's stated risks or open questions (if any), read against the confidence of its Diagnosis and Approach language. | Passes if every claim of cause or completeness is backed by quoted evidence, and any genuine unknown (an untested platform, an unmeasured cost, a maintainer question still open) is named as unknown rather than asserted as settled. Never changes the verdict; it flags dressed-up certainty for the summary. |  preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any `required`
check graded `fail` or `unclear` makes the verdict `reject`.
`unknowns-labeled` (`preferred`) is reported but never changes the
verdict. `unclear` is treated the same as `fail` everywhere above: a
plan this grader cannot verify from the package is a plan that is not
ready to build from.
