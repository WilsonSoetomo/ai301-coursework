# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (tool/library version, OS/platform, and any other component the issue's own trigger depends on, e.g. a driver, a shell, a browser). | The record names the version and platform, plus every component the issue specifically implicates. Fails if the environment is absent entirely, or missing a component the issue's trigger depends on (e.g. no driver named on a driver-specific issue). | required |
| steps-followable | The repro report's steps, read as a stranger with the stated environment would read them. | A stranger could re-run the exact actions from a stated starting state and reach the same shown output. Fails if a step references an unshared/private resource (a company repo, a config that isn't pasted in), or omits an action the platform requires. | required |
| artifact-shown | The repro report's output excerpt, log, screenshot, or transcript. | At least one concrete artifact is quoted or shown, not just described in prose. A real attempt that shows nothing happening (a genuine cannot-reproduce transcript) counts; an assertion with nothing shown ("confirmed," "happens every time") does not. | required |
| behavior-matches-issue | The artifact above, read against the issue's stated trigger and failure mode, and the report's own conclusion about what it shows. | Two shapes pass. (1) Reproduce: the artifact was produced by attempting the issue's actual trigger (the same input shape, flags, or code path named in the issue, not a substituted one) and shows the same failure mode the issue reports (same error type, same crash-vs-graceful outcome, same visual symptom). (2) Honest cannot-reproduce: the report attempted the issue's same underlying mechanism, concludes the failure did NOT occur, and names what it could not match. An imperfect or incomplete attempt is expected and fine here — a named gap in one precondition is not itself a fail as long as the report draws the honest "didn't reproduce" conclusion rather than claiming success anyway. Fails only when a reproduce is claimed but the trigger's core mechanism was swapped for a different one (a different flag, a different expression, an easier scenario that never reaches the failing path) or the shown outcome doesn't match the issue's failure mode. | required |
| claim-honest | The report's stated conclusion (expected/actual, or a cannot-reproduce write-up) against what its own artifact shows, including any stated or unstated deviation from the issue's target version/environment. | Every claim is exactly as strong as its evidence: no stronger language than the artifact supports, no root cause asserted without a shown trace, and any deviation from the issue's confirmed target (a different version, OS, or config) is named rather than left implicit while still claiming the match. An honest, well-evidenced cannot-reproduce passes this the same as an honest reproduce. | required |
| comms-specific | The candidate claim comment (and repro comment, if present). | States a specific, concrete intent tied to this issue (what was found, what's next) in the poster's own words. Fails on interchangeable self-assignment boilerplate or a promise (a timeline, a guaranteed fix) the poster cannot back. | required |
| repo-ai-policy | The repo-facts contribution policy's AI-use line, against the candidate comments. Treat every candidate package as AI-assisted work by default (this course's packages always are), so "the comment doesn't say either way" is not evidence that no disclosure was owed. | If the repo's stated policy requires disclosing AI assistance in comments, the candidate comment must contain an explicit disclosure statement (naming the tool and roughly how it was used) — its absence fails this check even if nothing in the package explicitly says AI was used. If the policy instead requires comments be in the human's own words with no AI-generated text, judge the comment's voice against that. If the policy is silent on comments, or reaches only PR code, this check passes automatically. | required |
| next-step-named | The candidate claim comment's stated plan. | Names one concrete next action (a file, a function, a specific thing to test) rather than stopping at "I'll look into it." Never changes the verdict; it's a quality signal. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. Any `required`
check graded `fail` or `unclear` makes the verdict `reject`.
`preferred` checks (`next-step-named`) are reported but never change
the verdict. `unclear` is treated the same as `fail` everywhere above:
proof this grader cannot verify is proof that is not ready to post.
